## Disagreements
- **RLY-307**, gold NO / pred YES (LOW), **false positive.** Webhook retry/backoff is a
  reliability change to an unchanged payload contract; the classifier read "webhook retry
  semantics" as user-relevant and over-flagged. Borderline and low-cost (over-documenting
  wastes a review slot; it doesn't create a gap).

Priority (on the 16 true positives): 4 HIGH↔MEDIUM↔LOW boundary calls off (201, 218, 220,
311). Still soft, still not worth tuning against yet.

## Verdict, what the hard test proved

**Recall held at 100% when the phrasing stopped giving the answers away.** That's the finding
that matters: the classifier wasn't just reading tells in v1, it genuinely infers user
impact from a bare ticket ("migrate to BullMQ, payloads unchanged" → no; "add IF/ELSE nodes"
→ yes). The v1 perfect score was suspect; the v2 perfect score is earned. The command's Task A
criteria, applied by a capable model, route documentation needs reliably.

**The frontier moved from recall to precision.** The only error is an over-flag on an
internal-with-a-developer-surface change (307). That's the cheap error, so this is a good
place to be, but it's the real edge now, not enhancement-blindness.

## Next hardening axis (for v3, if pursued)

Phrasing is hardened; **scenarios are still clean**, one unambiguous change per ticket. Real
sprints bring compound tickets ("refactor X *and* add user-facing Y"), vague one-liners, and
mixed internal/external work. That ambiguity, not wording, is where recall would finally
bend. A v3 would add a handful of those. Only then does tuning the classifier's rules earn
its keep; on the current set the rules are already at ceiling on the metric that counts.
